# ADR-019 — Sidebar のファイル行を作成日時の新しい順に並べる

Status: **Accepted**（2026-09-17）

Amends: U-024（並び順は名前順）

Related: U-005, U-024, ADR-013, ADR-016, `ui/ui-spec.md` §2 / §13, `domain/file-lifecycle.md` §5

## Context

U-024 では Workspace のファイル一覧を名前順と定めていた。名前順は一覧の表示が安定する一方、ノート名に日付やトピックを含めない運用では、直近に作成したノートの探索コストが高くなる。Quiet ではノートを時系列順に作成・蓄積する利用形態が中心であり、作成日時の新しいノートを上位に配置する方が目的のノートへ迅速にアクセスできる。

作成日時の情報源には、OS が保持するファイルの作成時刻（Windows および macOS で取得可能）を利用する。ただし、現在の保存処理には以下の技術的課題がある。

- **保存ごとに作成時刻が更新される**: Atomic save（`domain/file-lifecycle.md` §5）では、一時ファイルへ書き込んだ後に元ファイルへ rename する。rename 後のファイルは一時ファイルの作成時刻を保持するため、保存を実行するたびに作成時刻が保存実行時刻で上書きされる。これは Windows で確認済みであり、一時ファイルが別名で先行作成されるため、NTFS の tunneling も機能しない。

この課題を解決せずに作成日時順でソートした場合、一覧の実態は「最終保存日時順」となる。

## Decision

### 1. ファイル行は作成日時の新しい順、フォルダ行は先に名前順

Notes および Archive の各階層において、まずフォルダ行を名前順で配置し、その後にファイル行を作成日時の新しい順で配置する。フォルダ内部の階層にも同一規則を再帰的に適用する。

フォルダ行を先行配置するのは、フォルダ自体に作成日時を持たせないためである。フォルダを「内包する最新ファイルの時刻」でソートする案は、行順の変動理由を説明しづらいため採用しない。

作成日時が同一のファイルは名前順で並べる。Native が返却する一覧は従来どおり名前順を維持し、表示順の制御は Frontend のツリー構築時に行う。

### 2. 作成日時は OS のファイル作成時刻

`DocumentSummary` に `createdAt`（epoch ms）を追加する。値は OS のファイル作成時刻から取得する。作成時刻を取得できない環境では更新時刻で代用する。

### 3. Atomic save は作成時刻を引き継ぐ

保存処理の実行前に元ファイルの作成時刻を取得し、rename 後のファイルへ書き戻す。これは Native の責務であり、Frontend は保存処理によって `createdAt` が変動しない前提で動作してよい。

元ファイルが存在しない新規作成時は何もしない。また、作成時刻の読み書きに失敗した場合でもファイル保存処理自体は成功させる。作成時刻はソート用の情報であり、本文データの保全を優先する。

### 4. 作成日時の表示は Appearance の設定で切り替える

Settings の Appearance に「作成日時を表示」トグル（既定値: off）を追加する。on の場合、Notes および Archive のファイル行右端にローカル時刻の `yyyy-mm-dd hh:mm` を表示する。「サイドバーを詰める」と同様、常設 UI ではなく設定項目として提供する（`AGENTS.md` §4）。

Recent には作成日時を表示しない。Recent は Workspace 外のファイルを開いた順に並べる領域であり、作成日時はソート順の根拠とならないためである（ADR-013）。

## Consequences

- ファイル名の接頭辞（`01-`、`02-` など）による並び順の制御は機能しなくなる。並び順を選択する設定は現時点では追加せず、必要が生じた段階で検討する。
- 本 ADR の適用前に Quiet で保存されたファイルは、最終保存時刻が作成時刻となっている。これら過去のファイルに対する修復は行わない。
- ファイルの複製時は、新規ファイルとして現在時刻を作成時刻とする。ファイル名の変更時は rename 処理のため作成時刻を維持する。
- 作成日時の表示を on にするとファイル名に利用可能な表示幅が狭まるが、Sidebar の幅（226px）は変更しない。
- `buildTree` は Native が返却する順序に依存しなくなる。Native の並び順は、作成日時が同一である場合の tie-break にのみ作用する。
- 日時の表示形式は固定とし、Settings に書式設定の項目は設けない。

## Alternatives

### Front Matter の `created` を使う

不採用。Front Matter を保持しないファイルが多く、走査時に全ファイルの先頭を読み込む必要があり、5000 ファイルでの応答性要件（U-024）を損なうため。作成時刻を持たないファイルシステムへの fallback 手段としては将来的な検討余地がある。

### 更新日時の新しい順に並べる

不採用。編集のたびに対象行が一覧の先頭へ移動し続け、表示の安定性を損なうため。

### 並び順を Settings で選べるようにする

不採用。設定項目を不必要に増やさない方針（`AGENTS.md` §4）に反するため。名前順が必要となる具体的なユースケースが生じた段階で検討する。

### 作成時刻を引き継がず、保存順で並べる

不採用。実装コストは最小であるが、「作成日時」という表記に対して保存時刻が表示されることになり、UI 表示と実態が乖離するため。
