# ADR-012 — Splitのscroll同期

Status: **Accepted**（2026-09-05）

Supersedes: U-027（MVPでは同期しない）

Related: U-027, ADR-002, `ui/ui-spec.md` §6

## Context

U-027 は「MVPではSplit scrollを同期しない」と決めていた。
理由は「行対応の推定が外れたときに勝手にスクロールする方が邪魔になる」。

この懸念は正しい。ただし前提が「推定」であることに引きずられている。
本アプリのPreviewは自前のASTパイプラインで組んでいるので、
**行対応は推定ではなく、レンダリング時に確定させられる。**

同時に、Splitで書いていると、Preview側が今どこを映しているのかを
手で合わせ続ける必要があり、Splitの価値がそのぶん削られていた。

## Decision

**Splitのscrollを同期する。設定で切れる（`syncScroll`、既定ON）。**

### 割合合わせはしない

`scrollTop / scrollHeight` を合わせる方式は採らない。
コードブロック・表・画像のように「ソース1行に対して表示が高い」要素が1つあるだけで、
以降の全域がずれる。U-027 が懸念していた「勝手にずれる」はこの方式のこと。

### 行の対応表を持つ

1. Preview描画時、**トップレベル要素**へ `data-source-line` を振る
   （remark-rehypeが持つ position を使う。推定ではない）
2. Editor側は CodeMirror の `lineBlockAt` から、**同じ行**の縦位置を採る
3. 対応点の間は線形補間する。両端の外側は外挿しない

両者が同じ行集合を持つので、対応点そのものでのずれは0になる。

入れ子の要素まで振らないのは、必要なのが「画面の縦位置と行の対応」だけで、
段落の内側の行が分かっても精度が上がらないため。

`data-source-line` は画面表示のためだけの印なので、
`renderMarkdown` のオプション（`sourceLines`）とし、書き出しHTMLには付けない。

### 駆動は片方向ずつ

掴んだ側が駆動側になり、もう一方のscrollイベントは140ms無視する。
これを入れないと、互いを動かし合って震える。

### 基準は上端ではなく少し内側

画面上端から72px下の行を基準にする。上端ちょうどの行は視界に入りにくく、
「今読んでいる行」と合わない。

## Consequences

- Preview のHTMLに `data-source-line` が増える。sanitize schema で明示的に許可している
- 採寸（`getBoundingClientRect`）はlayoutを強制するので、編集のたびに1フレームへまとめる
- 対応点はPreviewのトップレベル要素の数。長文でも数百程度で収まる
- 画像の遅延読み込みでPreviewの高さが変わるため、`load` を拾って採寸し直す

## Alternatives

### 同期しない（U-027）

ずれる不快感はゼロ。ただしSplitで書く体験がそのぶん弱い。

### 割合合わせ

実装は10行で済む。上に書いたとおり、コードブロック1つでずれる。採らない。

### Editor → Preview の片方向だけ

U-027 の代替案。実装は半分になるが、Previewを読んでいる最中に
Editorを合わせられないので、読む側の使い勝手が落ちる。
